# Architecture

At the bottom this is (souffle) datalog. The idea is that the user will input things in some _very_ non-tech-expert-user-friendly way (viz., my ideal goal is for someone like Bob Stalnaker to be able to use this tool comfortably). This then would get translated to an intermediate representation (Haskell). The idea with this intermediate representation was largely practical—I wasn't really sure what I wanted the front end to look like—but there's also good grounds for it: it represents exactly the information that the user needs to tell the engine about the system. So whatever the front end eventually looks like, it just needs to have that information. 

At the level of Haskell is where the modularity comes in: if a system extends another, then the Haskell data structures get combined to form a new data structure. So the modularity is captured at the Haskell level; at the Datalog level, there is no sense in which the `Sentence` type in `intuitionistic.dl` is the same as the one in `classical.dl`, or that the one in `classical.dl` is a subset of the one in `K.dl`. 

I'm using Haskell because I didn't want to use python; I then thought to maybe use C since I want to otherwise practice C, but the intermediate specs are pretty naturally represented with dictionaries and C doesn't have dictionaries, and so to then deal with it as a series of arrays would have also been hell (great practice though arguably lol), so I decided to just use Haskell (which I also otherwise wanted to practice). Haskell's ADTs have also been great and have supplanted what I had before as the intermediate representation (which were .json files). 

The idea is that the datalog is _completely_ Hilbert-style; that is, the systems represented in the datalog _are_ (boring, dull, bad, no fun) Hilbert-style and the proof checker is ultimately just following a set of axioms and inference rules. However, I want the user to be able to use derived rules (like the deduction lemma) or cite previously cited theorems or say that something follows by "classical reasoning" (this will be the hardest to implement); the Haskell layer is meant to take care of those abstractions. Ultimately, the Haskell layer takes the user proof with those abstractions, unfolds the abstractions, and translates them into datalog for rote axiomatic proof checking.
