# Architecture

At the bottom this is (souffle) datalog. The idea is that the user will input things in some _very_ user-friendly way (my ideal goal is for someone like Bob Stalnaker to be able to use this tool comfortably). This then would get translated to an intermediate representation (.json files in the specs directory, which I do have). The idea with this intermediate representation was largely practical—I wasn't really sure what I wanted the front end to look like—but there's also good grounds for it: it represents exactly the information that the user needs to tell the engine about the system. So whatever the front end eventually looks like, it just needs to have that information. (Honestly, the .json files aren't even that bad so I might leave them as the front end for a long while lol.)

The .json representation then gets translated into Haskell (currently python) data structures. This is where the modularity comes in: if a system extends another, then the Haskell data structures get combined to form a new data structure. Since this is a new data structure, this technically isn't modular in the sense of e.g. pyrosome (I think). But it's good enough for me. 

I'm using Haskell because I didn't want to use python; I then thought to maybe use C since I want to otherwise practice C, but the intermediate specs are pretty naturally represented with dictionaries and C doesn't have dictionaries, and so to then deal with it as a series of arrays would have also been hell (great practice though arguably lol), so I decided to just use Haskell (which I also otherwise wanted to practice). 

Right now I've mostly worked on making the specs. I haven't really worked on making the proofs. Right now you can only do axiomatic proofs to the letter, i.e. no abstraction. But once I define a representation for proofs, then we'll get abstraction in the system, which is the entire point of this thing—the way we did axiomatic proofs in 24.244 was far removed from how axiomatic proofs in Hilbert-style reasoning feel.
