# Architecture
## Overview
At the bottom this is (souffle) Datalog. 

The user writes proofs in .txt files (the requirements of which are detailed in [`PROOFS.md`](PROOFS.md)). These are then parsed into a Haskell representation. This Haskell representation is where all the abstractions are unraveled such that the user proof with abstracted justifications (citing other proofs, using derived rules, deduction, etc) are translated into the corresponding proof without abstractions and with _only_ the logic's axioms and inference rules. Then, those lines are translated into Datalog. 

The Datalog defines a proof as proven if all of its lines are justified and among its justified lines is the statement of what was sought to be proved. A line is justified if it is an instance of the axioms, or if it follows from previous lines by an inference rule in the logic. Otherwise, it is not justified. 

At the level of Haskell is where the modularity comes in: if a logic extends another, then the Haskell data structures for the specifications of the two logics get combined to form a new data structure. (This process is recursive, so it goes all the way down.) So the modularity is captured at the Haskell level; at the Datalog level, there is no sense in which the `Sentence` type in `intuitionistic.dl` is the same as the one in `classical.dl`, or that the one in `classical.dl` is a subset of the one in `K.dl`.

### Note on defined operators
The Haskell type for defined operators, `DefinedOperators`, actually has no notion of an accompanying operator object. It just has a name (actually never used, I think), symbol (for parsing user input), arity (for internal things), and a definition, which is a function from a list of `Sentence` (the arguments) to a `Sentence`. It is on the user to make sure that the arity matches the length of the argument to the definition function; the only way I could think of to get around passing that onus onto the user is with some sort of dependent typing, since the type of the input to that function depends on the arity of the operator, which is an int (term). (Though, for anyone who happens to come across this, please let me know if otherwise!) Another not so good thing about the current setup is that the user has to interact with the Haskell `Sentence` type. It's nothing out of this world, but it's just a bit ugly and would probably (unlike, my hope is, the rest of `Specs` and sponge more broadly) take more than 10 minutes to learn for people not awfully comfortable coding. 

The fact that there is no accompanying `Operator` object for defined operators makes this approach different from the sort of approach in [model-checker](https://github.com/benbrastmckie/ModelChecker/blob/master/code/src/model_checker/syntactic/operators.py), another project where I had to think about how to do defined operators for a similar tool. In that project, which was originally written in python (currently being transferred to Haskell), defined operators are a sublcass of the operator class. Since Haskell doesn't have subtyping, directly lifting that approach (by having classes correspond to types) is not possible. The next closest thing would be to have a record type `DefinedOperator` that takes an `Operator` and a definition. I tried that initially (you can see the approach commented out in `Specs.hs` of commit ed5b17d to this repo), but the definitions got kind of ugly and recursive in a not-so-fun way (nothing terrible, but would seriously be deviating from the idea that just about anyone should be able to extend the system having only background in paper-logic-notation, so to speak), so I abandonded it. 

The current approach to defined operators is nice in that it better encapsulates what defined operators _are_ and what they are _not_: the are _not_ objects in our logic or in our proofs in any sense really, and they _are_ just a recipe to get from symbols that don't mean anything to ones that do. They aren't meaningful in that they (not only do not have meaning in the logics,[^1] but also they) never interact meaningfully with our reasoning about proofs (i.e., if they're in derived rules, they're there only as sugar—actually thinking that you could put them in derived rules, they'd just immediately get washed away since they're functions); they're always just a shortcut, one before all others. As a result, we don't have them be a type (or have part of their definition be a type) that interacts with how we manipulate proofs. To make them `Operators` (or have their type have a field with an `Operator`, as I initially did) would be to make them into a type that interacts with how we manipulate proofs. I suspect that's why the first approach was getting gross. 

However, even though an approach like the one in model-checker didn't work out in Haskell here, this is not to say that that gneeral approach is necessarily without merits in a language without classes/subtyping. In fact, part of the thing that made the general question of defined operators much harder in model-checker than here was that we wanted to print user-inputted sentences as the user inputted them. So if the user wrote `\box A`, we didn't want `\top \boxright A` to be printed; we wanted `\box A` to be printed. I don't remember to what extent that factored into the decision to make defined operators a subclass of operators, but I suspect it was nontrivial. For this project, I've so far decided that the proof checker should function more as a "this proof goes through" or "this proof doesn't go through," probably also getting into "these lines are justified" and "these lines are not justified;" in neither of those cases do we need to print user input, so that particular concern does not arise. (Also for model-checker we were much less concerned with immediate usability for people without a coding background, since part of the idea of the project was to get computational tools into philosophical logic/linguistics. What better way to get people acquainted with coding than by having them look and interact a little with code?)

[^1]: This raised the following funny thought: if you give the axioms and inference rules (i.e., give meaning to the logical operators, under an inferentialist view on semantics) using _only_ defined operators, what you've done is say how some set of symbols are to be used (your real operators), while never actually using those symbols and instead using another set of symbols (your defined operators). Because meaning for the inferentialist comes from use, it feels like you're effectively taking your defined operators as meaningful, since that's what you've actually used on the paper, and your primitive operators as mere abstractions, since you never actually use them! 

### Note on derived rules
Derived rules are a bit opaque. 

They depend on a `Transformant` data structure that is basically a list zipper. (I'm don't remember why I didn't call it that; maybe I should.) This list zipper is the data structure a proof is in while it is undergoing a series of changes via derived rules. As examples, there is a pass through a proof to check for deduction lemma invocations (`useDeduction`), and one to check for derived rule invocations (`applyDerivedRules`) (both are in [`Proofs.hs`](Proofs.hs) currently). (The order of these matters. Deduction is last, since the construction (proof) of the deduction lemma depends on only axioms and modus ponens. Thus, if a system has inference rules that conflict with the construction of the deduction lemma, like any normal modal logic, it will not go through.)

A derived rule can ultimately be defined by the user as just a list of prooflines that replace a given proofline (more specifically, a `Transformation`, which is just shorthand for `Transformant -> [Line]`, where the idea is that the resulting `Line`s replace the current actual like in the `Transformant` (zipper)). This, of course, introduces an offset to the line numbers, and this is handled largely automatically with the `applyTransformation` function, which is I think the biggest benefit of doing derived rules with this complicated data structure. 

There are some examples of basic derived rules in the [`Defs/Rules.hs`](Defs/Rules.hs) file. They are a bit uglier than I'd like. I added substitutions for parsing sentences to the Haskell such that in principle the `Sentence` data type can still basically be avoided by the user (even as someone familiar with it since I wrote it, it is much nicer to write in infix notation than in the prefix notation of the `Sentence` type, so this regardless is a plus I think even if the resulting code is still not that newcomer-friendly).

## Optimizations
### Pruning proof trees
If you just unfold successive uses of derived rules, cited theorems, and deduction, you can get rather long proofs. For example, take `currying_prime`. This proof invokes deduction three times and then cites two other proofs. (It is verbose on purpose.) What sponge does is first it unfolds derived rules in the Haskell proof (which is just a list of `Line`s). This is usually a couple of lines (in this case it is just a couple). Then, it plops the cited theorems, fully unfolded, into the Haskell proof. This brings the proof from about 10 lines to about 50. Then, it applies the deduction transformation three times. This results in a datalog proof that is almost 3k lines long! Understandably, Datalog takes a few seconds (about 10) to solve this. (NOTE: with a shorter version of one of the theorems `currying_prime` depended on, these results are less drastic, but I left the old version in that file to play around.)

Can we do better? The reason the Datalog proof is so long is that successive invocations of deduction cause the proof to grow geometrically. Moreover, deduction needs to happen after proof citation and derived rules, so the geometric growth is exaggerated from the number of lines the user sees. The growth is also following a rather crude procedure, meaning there are often repeated lines. We can do better by just removing the repeated lines, and any lines that are only used to get to repeated lines. 

More specifically, we can imagine a proof as a directed acyclic graph, where nodes with no children are axiom invocations and nodes with children are inference rule invocations, where the children are the line numbers referenced in the inference rule. (This would be much easier with drawings, sorry.) The graph would have a source: this is the last line, which has the statement of the theorem at hand. 
For any node in the DAG, all nodes you can reach from it (I'm assuming an inference rule node points _towards_ the lines it cites, not that they point towards the inference rule node) are the lines that are used to justify that node. For any given line node in our proof DAG, lets call the subgraph of nodes it can reach its subproof. Now imagine that there are two lines in our proof that have the same content. Since they are two different lines, they have different subproofs. However, since they have the same content, we only need _one_ of the lines, since wherever we cite one of the lines for its content we could have just cited the other. So, we can prune our proof tree by choosing one of these two lines and up the tree from the line we remove, replace references to that line with the line we keep. In graph-speak, say we have lines i and j with the same content. Say we choose to remove line i, along with its subproof. We can accomplish this by having any edges that point to line i (i.e., any inference rules that cite the result in line i) instead point to line j. 

How do we choose which line to keep? A tempting answer is the one with the smallest subproof. However, it may be the case that this is the line from those with the same content highest up, and there are lower lines that reference the result (from the lower subproofs). If we keep the highest line, we'd be breaking the fact that inference rules can only cite smaller lines. Datalog enforces this and Haskell assumes this when manipulating proofs, so we should avoid this. <!-- (I think this corresponds to the property that the topological order of the DAG follows the ordering of the integers, ie larger nodes are always closer to the source in the topological order, or more specifically you can flatten the topological order in such a way that... etc.) --> 
However, in practice this seems to work. It may just be that the smallest subproof tends to be with the lowest line number. This makes intuitive sense for two reasons: first, the lower line numbers have less available lines for their subproof, and second, since these repetitions tend to come from deduction lemma citations, they tend to occur within the same subproof; if they occur within the same subproof, then of course the lower subproof is smaller, since it is a subproof of the bigger subproof. 
In any case, the moral way to get around this would be to change the line numbers of the smallest subproof to be available smaller line numbers. These are available: whatever line numbers were used by the subproof the smallest line, that subproof was larger by assumption, so we could fit within those line numbers the entire smallest subproof that is higher up. However, to do this would be more complicated than I would like to dedicate the time to, and I'm not sure how much more it would make the tool more usable: I think people would be willing to wait a few seconds for sponge to tell them if their proof is right. (Maybe anything more than 10 seconds is too much.) (And up to now, the naive implementation has worked.)

This is implemented in [`PruneProofTrees.hs`](PruneProofTrees.hs). The optimization takes the length of the `currying_prime` proof from nearly 3k Datalog lines to about 1.2k. (Note: with the optimization below, this is now at ~600 lines.) For other proofs, it brings down length anywhere from 10 lines for shorter (<50 lines) proofs or made smaller by a factor between about 2 and 6. (The more deduction invocations, the higher the factor. Each deduction invocation about triples the length of a proof)

If the naive solution currently implemented to the picking repeated content problem ends up not working, implementing the moral solution to the smallest subproof part detailed above may make the optimization a lot better, but I don't know how much it'd be worth it, for a couple reasons:
1. The `currying_prime` proof takes a few seconds for Datalog to check when using the smallest line number version, but it isn't _that_ bad, and I made that proof long on purpose, specifically to see how the optimization would do on a long proof. The 1.2k line proof takes about 5 seconds on my machine, while the 3k line proof takes 10 seconds. (Update: after improving how cited proofs are done, the proof is now 588 lines and takes about a second on my machine.)
2. Proofs seem to get particularly long when you apply many deductions and cite other proofs. However, for modal logics (with necessitation), which is what this tool was originally designed in mind for, deduction isn't even available, so this shouldn't be too much of a problem there. 
3. Currently, the optimization picking the lower line number and the optimization picking the smallest subproof do very similar. (As discussed above, we have reason to think the smallest subproof tends to be the lower one.)

### Simulating cut on proofs using the deduction theorem
This optimization can be thought of as a simulation of the cut rule. I say simulation because the cut rule depends on hypothetical judgements `G, A |- B`, which we don't have in an axiomatic setting. We instead simulate hypothetical judgements with the deduction lemma transformation. This is an optimization because it lets us avoid unfolding the deduction transformation from `A |- B` to `|- A -> B`, which makes a proof substantially longer. (I borrow heavily on vocabulary from [Martin-Löf](https://github.com/michaelt/martin-lof/blob/master/pdfs/Meanings-of-the-Logical-Constants-1983.pdf).)

In an inferentialist order of explaining the meaning of logical constants (e.g. Brandom, Martin-Löf), we have _inferences_ (proofs; these are actions we take and are represented with judgements on either side of a horizontal line), _hypothetical judgements_ (`A |- B`), and judgement (of the truth) of an object-language conditional (`|- A -> B`). An object-language conditional _makes explicit_ the _reasoning_ encapsulated in the hypothetical judgement, which, when we have an _actual_ judgement `|- A`, makes our _doing_ the inference from `|- A` to `|- B` valid. 

In an axiomatic setting, we have no hypothetical judgements (`A |- B`); we only have absolute judgements (`|- A`). We can, however, (in limited cases, viz. not when we have necessitation) _simulate_ hypothetical judgements, with the deduction proof, that any proof of `B` with an assumed proof `A` can be mechanically turned into a proof of `A -> B`. (I say this is a simulation because our object languages have no notion of hypothetical judgement; we operate with this notion but it then gets compiled away.) This simulation turn the short conditional proof of `A |- B` into a long proof of `|- A -> B` (usually about 3-4 times longer). 
<!-- OLD: In proving things axiomatically, we can _suppose_ things that we then _say_ we are supposing in our theorem. If you look at the meaning of the conditional as an expression, a making explicit, of the _act_ of inference, the deduction lemma amounts to taking some meta-level action (supposition) and codifying it in the object-level. We shouldn't need to codify meta-level actions in the object-level if we can replace the meta-level suppositions being codified with object-level assertions, as is done in derived rules. In other words, if we happen to _actually have_ what were the suppositions in the deduction lemma, we shouldn't need to _say_ we are supposing them (i.e., unfold deduction) and then apply them; we should be just use them as they were used in the proof where we supposed them. -->

Here comes the problem: for some particular `A`s and `B`s, I have proofs of `|- A -> B`, and I also wanted to make derived inference rules of the shape
```
|- A
------
|- B
```
For a concrete example, consider the inference rule
```
P -> Q   Q -> R
-------------------
P -> R
```
and the inference rule
```
P -> Q
---------------------
(Q -> R) -> (P -> R)
```
and the theorem `|- (P -> Q) -> ((Q -> R) -> (P -> R))`. The (unconditional) judgement gives us a proof of contraposition, the first inference rule gives us hypothetical syllogism,[^2] and the second gives us an inference rule for contraposition. 

[^2]: Though hypothetical syllogism is actually implemented in sponge with a different proof, `|- (Q -> R) -> ((P -> Q) -> (P -> R))`, since it's a bit shorter. 

The way you justify inference rules of that shape is by, from having a proof of `A`, getting one of `B`; since this is for future cases where we _will_ have the proof of `A`, its construction is very similar to the proof of the hypothetical judgement `A |- B`. (In more concrete terms, it's exactly the same as a deduction version of the proof, except we don't have "Assumption" lines and references to "Assumption" lines are replaced by references to cited lines, which have the content `|- A`.) You can _very_ intuitively justify `|- A -> B` by simulating a proof of a hypothetical judgement `A |- B`. In fact, that's the point of the deduction lemma, which we can state as an inference rule (relevant later): 
```
A |- B
---------
|- A -> B
```
So here is a problem: I'm writing derived rules, which _look_ like `A |- B`, and I'm also writing proofs, which _look_ like `A |- B`. Ideally, since they're basically the identical in writing, I write them only once! What's worse, say a user wants to define a derived rule based on a proof; they'd need to add it in two places, one of which is horrendous to work in. 

Here is a first solution: only write the proof `A |- B`, which then gets translated into `|- A -> B`, add that to your proof, and then since you have `|- A` use modus ponens to get `|- B`. However, this runs into a purely practical problem: the proof of `|- A -> B` from `A |- B` is quite long, and then we have to add another line to do modus ponens. 

We can improve on that solution by taking the inferentialist way of thinking about this (which was implicit above) seriously. Particularly, we are proving that we can _say_ `|- A -> B` by proving that we are justified in taking a hypothetical judgement `|- A |- B`; a hypothetical judgement, when you replace the supposition with an _actual proof_ becomes a _bone fide_ inference from `|- A` to `|- B`. In these derived rule cases, given we have a proof of A and a proof that _if only_ we had a proof of `A` we'd have one of `B`, why can't we _actually take_ that proof of `A` and go to `B`? Expressing this a bit more concisely, I am looking to be able to do this:
```
|- A   A |- B
----------------
|- B
```
Which looks like Cut! For logics without necessitation as an inference rule, we are able to do this, since those are the ones in which we can simulate the hypothetical judgement `A |- B`. (I would like to stress that there really never is a place where there is a proper hypothetical judgement in an axiomatic system. There are only absolute judgements, and the deduction construction/proof shows that we can _simulate_ hypothetical judgements.) 

We can even generalize this. Suppose we've proven a conditional `|- A -> B -> C`, by using deduction, i.e. simulating the hypothetical judgement `A, B |- C`. Given a proof with `|- A`, we'd like to be able to conclude `|- B -> C` similarly to how we deduced `|- B` in the cut above. The following derivation would allow this:
```
|- A    A, B |- C
-------------------
B |- C
------------
|- B -> C
```

The optimization implements this.[^3] It is currently in [`Abstraction.hs`](`Abstractions.hs`) though may move to its own file if that one gets too big. 

[^3]: More specifically, when a user wants to cite a theorem that uses deduction in its proof and apply it to previous lines, sponge checks to see if the user proof uses deduction. If it does, then it won't expand the user proof for the derived rule, instead replacing the `Assumption` lines in that proof with references to the lines the user wants to apply the theorem to. The result is then added to the user's proof. Thus, for a theorem that has a related derived rule, the user only needs to write one thing, the proof, and using derived rules similar to it result in an extension of the user's proof by the number of lines in the user's proof (minus assumption lines). For example, using hypothetical syllogism becomes a 5 line addition to the user's proof, instead of the 30 line addition in the `hypothetical_syllogism.dl` file, or a 5 line addition based on a derived rule defined in `Defs/Rules.hs` (now commented out or deleted). 

For some more practical details: this solution cut down the length of some proofs, and made defining derived rules that come from theorems rather easy. For example, the length of the datalog proof for `contrapositive_backward` was at about 200 lines, but with this it came down to 115 lines. Moreover, since the user defined proof of `contrapositive_backward` uses deduction, using the proof as a derived rule (`~Q -> ~P |- P -> Q`) results in only a ~30 line addition to the proof it's being used in since it avoids the deduction in the proof of `|- (~Q -> ~P) -> (P -> Q)` (see [`test_contrapositive_backward`](user_proofs/classical/test_contrapositive_backward.txt), or [the proof of the dual of axiom 4 in S4](user_proofs/S4/fouraxiom_dual.txt)). The optimization means that using deduction can actually be advantageous, which is not the case at all for a simple implementation of an axiomatic proof checker. This also allows the user proofs to operate nearly completely at a higher level of abstraction, at the level of deductions and inferences, away from the two (kind of opaque) axioms that let you simulate deduction in axiomatic systems.
